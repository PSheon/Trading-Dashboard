# 決策紀錄

現行設計在 [Solana 聰明錢包研究系統 Spec](Solana%20聰明錢包研究系統%20Spec.md)。這裡記的是「為什麼這樣設計」：每個決策背後的實驗與數字，依時間排列。舊版 spec（rev 2 至 2.4）在 git 歷史中。

## 2026-09-29 範圍收斂為「point-in-time 研究層」

**起因**：功能不斷擴張（管線、漏斗、UI、部署、進度面板），但「指標能否預測跟單報酬」這個唯一重要的問題一直沒被回答；P1 還沒驗收，後面的階段就已同時開工。

**調查**：GitHub 與網路上已有大量相關工具。
- 錢包 PnL 與標籤：GMGN OpenAPI、Vybe Network、Birdeye。
- 找聰明錢包：smart-money-tracker（思路與我們的漏斗幾乎相同）、tracced、Smart_Money_Follower（包裝 GMGN）。
- 錢包追蹤與跟單機器人。

沒有任何一個提供 point-in-time、沒有存活者偏誤的錢包選擇回測，而所有排行與標籤都是「現在」的值。

**決策**：只自己做不可替代的部分（漏斗重播、歷史快照、回測、Helius 正確性基準），其餘改用現成服務；凍結 UI 與部署。

## 2026-09-29 GMGN 與 Vybe 實測

用 GMGN 的公開測試 key，對同一個漏斗錢包 `E1ouZN…JHT5` 與我們的 Helius 管線逐筆比對：

| 項目 | 結果 |
| --- | --- |
| 歷史深度 | activity 分頁取到 1,844 筆，回溯到錢包首筆入金（2026-07-24）；完整歷史約 31 秒 |
| 覆蓋 | 我們的 1,353 筆交易 GMGN 全部都有，買賣方向 100% 一致 |
| token 數量 | 89% 完全一致 |
| GMGN 多出 491 筆 | 同一筆交易賣出多個代幣時，GMGN 拆成個別賣出；我們歸為 complex，計入成本未知。是我們 26% 未完成回合的主要來源之一 |
| SOL 金額 | 買入我們約高 3%、賣出約低 4%，小額交易差距最大可達 48%。GMGN 報的是池子側金額，不含交易機器人（Axiom）的費用；我們報的是錢包實際付出與收到的金額 |
| 其他欄位 | USD 金額、gas、priority fee、tip、首筆入金來源、標籤（例如 arbitrager、axiom） |
| 速率 | 免費方案漏桶 5/5，錢包請求權重 3 |

**含義**：
- GMGN 的 PnL 會高估使用交易機器人的錢包；評估跟單要用自己模擬的成本。
- 回測只需要領頭交易的時間與代幣，跟單者成本另外模擬，所以 GMGN 的池子側金額可以直接用。
- GMGN 對多代幣交易的拆解比我們完整，可作為 complex 交易的分配依據（開放問題）。

Vybe：PnL 端點的解析度只有 1d、7d、30d、Full，時間序列只有最近 7 天；免費方案每分鐘 4 次、每月 12,000 credits，只適合少量查詢。

## 2026-09-28 擴大到 50 個漏斗錢包

**資料量**：16.8 萬筆交易、5.7 萬個已平倉回合、原始資料 1.7 GB；最大的錢包 180 天壓縮後 415 MB。

**資料品質**：
- 26% 的已平倉回合不完整：13,058 個成本未知、1,233 個有轉出。
- 12% 的交易是穩定幣計價（P0 樣本只有 1.7%）。
- 代幣主檔只覆蓋 14% 的 mint，受每次同步上限限制。
- 已評分的 7 個錢包中只有 1 個整體獲利：「能抓到飆股」不等於「整體賺錢」。

**規模化後才出現的缺陷**（皆已修）：

| # | 缺陷 | 修正 |
| --- | --- | --- |
| D11 | Helius Parsed Events 屬於 enhanced API，免費方案每秒只有 2 次，卻用了每秒 10 次的限流 | 依 API 類別分開限流 |
| D12 | 固定限流，重試不經過限流器 | 自適應限流（429 時加倍，成功後恢復） |
| D13 | 請求沒有逾時，一條死連線讓 job 空等一小時 | 60 秒逾時 |
| D14 | 原始檔一次解壓成一個字串，超過 512 MB 上限 | 串流讀取 |
| D15 | 入庫沒有錢包層級的錯誤隔離 | 失敗錢包留待下一輪 |
| D16 | 修補只涵蓋本輪抓到的錢包 | 涵蓋本輪入庫的全部錢包 |
| D17 | 回補沒有上限 | 首次回補最多 500 頁，歷史起點改為實際最早時間 |

## 2026-09-28 發現漏斗首次執行

定義與參數在 spec 的回測設計中。開發時修正了兩個會嚴重扭曲結果的錯誤：

- **畢業判定太寬**：把「curve 之後第一筆 PumpSwap 交易」當作畢業，會把事後手動開池的廢棄 curve 算進來，14 天得到 13,838 個。改為 curve 最後一筆交易後 10 分鐘內出現 PumpSwap 交易，得到 6,965 個。
- **最高市值被扭曲**：用單筆成交價算峰值，前幾名高達數千萬 SOL。原因不是 Dune 的小數位數（實測供給 10 億、小數 6 位，換算正確），而是池子被抽乾後的極端成交價，以及建立當下 curve 就被整包買走的 bundle 發射。改為每小時成交量加權均價，並要求該小時成交量 ≥ 10 SOL、至少 5 個錢包；另外排除建立後 60 秒內就畢業的代幣。修正後，峰值中位數 282 SOL、前 10% 為 992 SOL。

**排名**：依入選代幣數排名時，前段全是高頻機器人（158 次入選、只賺 1.3 SOL）。改為依獲利排名、k = 3、每天交易數上限 50。

## 2026-09-28 架構審查（D1–D10，皆已修）

| # | 缺陷 | 修正 |
| --- | --- | --- |
| D1 | 讀取再改寫沒有互斥：頁面新增的錢包會被每日 job 覆寫 | 行程內與跨行程的寫入鎖 |
| D2 | 快照存檔沒有失效機制 | 增量維護（`snapshot_dirty`），加上 `verify` 重算比對 |

| D4 | 單一錢包失敗中止整輪 job | 錢包層級隔離 |
| D5 | 分頁遇到空頁就停 | 以 `paginationToken` 為準 |
| D6 | 歷史快照列出當時還沒發現的錢包 | 預設隱藏 |

| D8 | spec 與程式不一致 | 改寫 |
| D9 | 舊檔案缺少新欄位就讀不出來 | 依名稱聯集補 NULL |

**驗證**：180 天的快照逐日重算比對 180/180 一致；P0 的 5 個錢包對帳可信列 726/726 一致。

## 2026-09-28 改寫為 TypeScript

資料格式不變。改寫後在 P0 的 5 個錢包上，trades、token_transfers、lots、positions 與 Python 版逐列相同，指標差距 < 2×10⁻¹⁶。負數金額的拆分改為向下取整，與 Python 一致。

## 2026-09-28 P0：來源驗證（5 個錢包，約 5,400 筆交易）

| 項目 | 結果 |
| --- | --- |
| 交易粒度 | 確定為 (tx\_sig, wallet, mint) 的餘額淨變化；多跳路由收斂為錢包實際付出與收到的數量 |
| Helius 與 Dune 的覆蓋 | 92.1% 一致。Dune 獨有的是多跳路由的中間 token 殘值；Helius 獨有的是 Dune 未解碼的路由 |
| token 數量 | 97.1% 一致；其餘是以 token 收取的 1% 費用 |
| 場所 | PumpSwap 76%、bonding curve 16%、其他 12 個 project 8%，所以交易序列不能限定場所 |
| 遺漏 | 用錢包地址查歷史，會漏掉只碰到其 token 帳戶的交易；修補後對帳 809/809 |
| 同 slot 排序 | 用 `transactionIndex` |
| 成本 | 回補平均每錢包 124 credits |

**決策**：錢包歷史只用 Helius，Dune 負責漏斗與代幣主檔；pump.fun 畢業後遷移到 PumpSwap（2025-03 起），不是 Raydium。
