## 2. 現在的證明方式（`copy-funding-evidence.ts`）

入帳要同時符合兩份資料：

1. **跟單帳戶的帳本**（一般 API `userNonFundingLedgerUpdates`）裡，有一筆 `internalTransfer`：
   - 來自使用者主錢包；
   - 進到這個跟單帳戶；
   - 金額和手續費正確。
2. **explorer 的交易明細**（`txDetails`）裡，同一個交易 hash 是：
   - 主錢包簽的 `usdSend`；
   - `time` 等於我們簽名時用的 nonce；
   - 鏈別、目標地址、金額都正確。

第 2 項的作用是證明「這筆就是我們請使用者簽的那一筆轉帳」，而不只是「有一筆金額一樣的轉帳」。

| 檢查項目 | explorer 交易明細 | 只用帳本 |
|---|---|---|
| 由使用者主錢包轉出 | ✅ | ✅ |
| 轉到這個跟單帳戶 | ✅ | ✅ |
| 金額、手續費 | ✅ | ✅ |
| **是我們簽的那一筆**（nonce 吻合） | ✅ | ❌ |
| 正確的鏈與網路 | ✅ | 由查詢的網路隱含 |

## 3. 只用帳本會有什麼風險

只用帳本時，唯一無法排除的情況是：**主錢包在同一段時間內，對同一個跟單帳戶，另外又轉了一筆一樣金額的錢**。

這種情況幾乎不會發生：

- 跟單帳戶是這次設定**新建的地址**，只有這次入金會轉錢進去；
- 主錢包是使用者的 Privy 嵌入式錢包，要使用者本人簽名才能轉帳；
- 即使真的發生，錢也是轉進使用者自己的跟單帳戶，不會流到別人手上。最壞的結果只是把另一筆轉帳當成這筆入金，入帳金額一樣，帳也不會算錯。

## 4. 提案

保留 explorer 為主要證明方式，**只在 explorer 確定無法使用時**，才改用帳本做有條件的確認：

1. **啟動條件**：explorer 連續失敗超過 **10 分鐘**（例如逾時、5xx、DNS 失敗）。只要 explorer 有正常回應，就照現在的方式確認，不走備援。
2. **唯一性**：從這筆入金送出起，到現在為止的帳本裡，主錢包轉到這個跟單帳戶、金額相符的 `internalTransfer` **只能剛好一筆**。
   - 零筆：繼續等。
   - 兩筆以上：維持「待確認」，不自動入帳，交給管理員處理。
3. **時間範圍**：那筆帳本紀錄的時間，必須落在我們簽名的 nonce 前後 5 分鐘內。
4. **留下紀錄**：入帳收據標註 `proof: "ledger_only"`，記下 explorer 失敗的起訖時間，管理後台看得到是哪一種證明。
5. **事後補驗**：explorer 恢復後，背景重新查一次這筆交易明細。
   - 如果吻合：收據補上 explorer 證明。
   - 如果不吻合：通知管理員，並暫停這個跟單的新開倉，等人工確認。

## 5. 測試（實作時要做到，而且每項都要先在舊程式上確認會失敗）

- explorer 正常時：行為完全不變，所有現有測試照舊通過。
- explorer 失敗未滿 10 分鐘：不入帳。
- explorer 失敗超過 10 分鐘、帳本剛好一筆相符：入帳，收據標 `ledger_only`。
- 帳本有兩筆相符：不入帳，維持待確認。
- 帳本那筆的時間超出 nonce 前後 5 分鐘：不入帳。
- explorer 恢復後補驗：吻合就補上證明；不吻合就通知並暫停新開倉。
- 本機 harness：模擬 explorer 無法連線，完整跑一次設定到開始跟單。
